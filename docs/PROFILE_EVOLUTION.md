The profile connects readers with Albert Tan Sin Hon's research, experimental
tools, teaching materials, collaborators and scoped paid-work enquiries.
Improve it when evidence or reader needs change.

## Ownership and rhythm

The existing GitHub Adoption workflow owns routine profile editing. It reviews
the profile daily around 11:00 Asia/Singapore and makes a fuller review each
Saturday. Academic GitHub Development supplies implementation receipts;
GitHub Community Care supplies actual reader questions and contribution feedback;
GitHub Release Readiness supplies verified release evidence.

Use the existing workstreams and shared work limit. Check current main and open
work before editing so two workflows do not publish competing changes.

## A useful review cycle

1. Read the current profile, linked project READMEs, relevant releases and open
   contribution paths. Consult original publication records when scholarly
   status might have changed.
2. Identify one evidenced problem: an obsolete claim, broken entry point,
   confusing explanation, missing useful result, or friction in making a
   relevant collaboration or paid-work enquiry.
3. Choose the smallest substantive change that addresses it. State the expected
   reader benefit and the evidence that would show whether it helped.
4. Review the complete diff, check changed links and repository paths, preserve
   licences and attribution, and verify factual claims against their sources.
5. Publish the authorised change with an expected-head guard, then inspect the
   rendered result. Record the exact commit, evidence and remaining uncertainty.
6. On later reviews, assess actual feedback and outcomes before expanding the
   change. If there is no useful change, leave the profile alone and record the
   check in the existing private operating record.

The displayed update date changes only after a substantive profile update.
A scheduled review alone is not a publication or an observed outcome.

## What merits an update

- A verified project release, material limitation or improved first-run route.
- A publication's status changing in its institutional or publisher record.
- A real contributor finding, accepted improvement or documented independent run.
- A clearer description of a scoped service supported by delivery capacity.
- A broken link, inaccurate licence statement or obsolete project priority.

Keep the opening concise and the project table easy to scan. Preserve research,
teaching and music as distinct parts of the portfolio. Retain useful historical
material with its status clearly labelled.

## Evidence and boundaries

Use primary sources for scholarship and current repository evidence for software.
Label synthetic examples and AI assistance accurately. Distinguish internal
checks, independent human review, external use and accepted customer work.

Keep private customer records, commercial negotiations, financial targets,
receipts and account information out of GitHub. Public testimonials or case
studies need permission and evidence. Revenue claims need actual receipt and
delivery records; traffic, stars, proposals and invoices measure different things.

Maintain the current reuse terms. A public repository is not automatically open
source. New licences, paid obligations, financial accounts and grant terms require
the appropriate owner decision.
